Scope: the whole repository at `4be4b52`, with emphasis on how easily a new
reader can understand what the system does, what is proved, and how. The
companion deliverable is the new [guided tour](../GUIDE.md).

## Overall assessment

The core is in good shape. The interpreter (`Core/Interp.lean`) and guard
(`Core/Guard.lean`) are short, well commented and readable; the headline
theorem statements in `Statements.lean` are plain and each has a docstring in
ordinary language; non-vacuity witnesses exist for every main theorem; and
the proofs build and pass Comparator as claimed. The commit service's
authentication and Lean supervisor are careful (pinned issuer, audience and
algorithm; constant-time token comparison; bounded queue; kill on timeout).

The main obstacle to understanding is not the code but the **documentation
layer around it**: the entry points had drifted from the code, labels were
defined only in an archived brief, and the README has grown into a status log.
The findings below are ordered by how much they slow a new reader down.

## Findings

### Fixed in this change

1. **VERIFICATION.md pointed to the wrong lines.** All 18 file:line references
   in the headline theorem table were stale (for example `T0.lean:151` for a
   theorem at line 139), as were most references in the property, renderer,
   definition and seed tables, and the generated appendix had been produced at
   an older HEAD that is not in this repository's history. Fixed: every
   hand-written reference now resolves to its declaration, and the appendix
   was regenerated by `scripts/audit-verification.sh`.

2. **The checker-soundness theorems were hard to find.** The README's "Read the
   Lean" presented `Statements.lean` as *the* Comparator challenge. The
   theorems behind the central claim, that acceptance implies properties 1–5
   and 7–13 (`accepted_*`), plus T7 and T8, are in a second challenge,
   `Ehr/Check/ComparatorStatements.lean`, and the completion fragments in a
   third. Nothing explained how to run them. Fixed: README and the guide name
   all three, and `make verify` runs the build and all three challenges.

3. **Labels were undefined or ambiguous.** T0–T11 are defined only in
   `docs/hackathon/BRIEF.md`; D1–D6 in `docs/design/core-model.md`. The README
   cited "gap G2" and "gap G3", but no gap list exists in the repository, and
   in the brief G1–G8 are *goals* (G3 is "a declarative UI program format").
   Fixed: a glossary in the guide; the README and `concurrency.md` now say
   "client-side guard" and point to the deployment-gaps section in words.

4. **Stale statistics.** The README's counts (245 files, 42,927 lines, 693
   theorems) and per-area table had drifted, and the table omitted `Sem/`,
   `Commit/` and `Multi/` (about 3,400 lines). Updated with the counting
   method stated.

5. **Owner-specific paths in executable code.** `Makefile` (`explore-test`),
   `explore/cli.ts`, `baseline.ts`, `review.ts`, `screenshots.mjs`,
   `explore/decision-server.sh` and `app/tests/dashboard-performance.test.ts`
   hard-coded `/home/saithat/...`. `scripts/publish-partial.mjs` also
   *overwrote* any `TMPDIR` the user had set, although the README tells users
   to choose a `TMPDIR` on the same filesystem as `runs/`. Fixed: binaries
   resolve relative to the repository; scratch defaults to `$HOME/run-tmp`
   and respects an existing `TMPDIR`. README command blocks use the same
   convention. Historical audit reports keep their recorded paths.

6. **A data-dependent test failed instead of skipping.** The README says
   archive-dependent tests skip with an extraction hint.
   `app/tests/dashboard-performance.test.ts` read `runs/core-10day-live` at
   module load, so the whole file failed on a fresh clone. Fixed with the
   existing `withData` helper; its two self-contained tests now run.

### Recommended (not changed here)

Lean sources were deliberately left untouched: the WASM manifest hashes every
Lean source byte (comments included), so any Lean edit makes `make wasm-check`
fail and invalidates recorded certificates until the owner rebuilds and
rebinds. Items 7–11 therefore need an owner-scheduled rebuild.

7. **A trusted definition's docstring contradicts its body (high).**
   `Props/Navigation.lean`: `NavigationSane` says it "observes `uiNav`; it
   does not invent a second navigation model", and the module header says
   "the property uses the same tree that clinicians see". The body is
   `Render.NavSane`, which checks `uiOverviewNav`, and `Render/NavRules.lean`
   says that overview "is not a certificate" for interactive navigation.
   VERIFICATION.md §8 already lists aligning D5 as open; until then, correct
   the docstring so the trusted surface does not overclaim.

8. **Soundness proofs have no explanatory headers (medium).** 127 of 279
   modules under `lean/Ehr` and `lean/Audit` lack a module docstring,
   including most `Check/*Sound.lean` files that carry property 1–13
   soundness. 1,294 of 4,868 declarations lack a docstring (Check 385,
   Render 274, Sim 214, Sem 163). A three-line header per `*Sound.lean`
   ("invariant X; preserved by `stepCore` and `runMacro`; static premise from
   rule Y") would make the invariant pattern visible. The guide's §6 describes
   that pattern in the meantime.

9. **Proofs select checker rules by position (medium).** For example,
   `PartialSound.lean` destructures `check_ok_iff` with
   `rcases hall with ⟨_, _, _, …, hr, _, hl, _, hp, _, _⟩`, about 20
   positions. A reader cannot tell which rule `hr` is without counting
   entries in `rules`, and inserting a rule breaks several files. Prefer one
   named lemma per rule (`rule_reviewsPinned_of_check : check … = .ok →
   reviewsPinned sp p = true`).

10. **The trusted type file mixes in simulation types (medium).**
    `Core/Types.lean` (1,208 lines) is on the Comparator trusted surface, but
    its second half defines simulator and CLI types (`Workflow`,
    `PersonaParams`, `TraceEvent`, `TaskMetrics`, `DayResult`, `Verdict`,
    `Certificate`). Splitting these into a `Sim/Types.lean` would shrink what
    a reviewer must read. Similarly, `Proofs/T0.lean` imports
    `Examples.TinyTests` and `Core.Tests`, so test fixtures enter the
    Comparator solution's import graph.

11. **Stale or duplicated Lean text (low).**
    `Specs/AlertUrgency.lean` says the policy is "pending owner review"; the
    README records owner approval on 2026-11-02. `Canonical/Tests.lean` and
    `Canonical/CoreWorkflowTests.lean` (and `BadTests` / `CoreBadTests`) are
    near-duplicates with identical module docstrings; say which profile each
    serves. Remove the unused `simp` arguments flagged by the linter.

12. **The README is a status log (high, for onboarding).** At 1,380 lines it
    combines the pitch, the proof table, architecture, dated audit narratives
    (WCAG counts, worker benchmarks, lock-file semantics, promotion reruns)
    and long command transcripts. A newcomer cannot tell which paragraphs are
    current design and which are history. Suggested split: keep the pitch,
    the "What is proved" table, architecture and "Run it" in the README; move
    "Semantic properties and extensions", "Exploration", the screen-gate
    operational detail and "Development checks" into `docs/` pages; link the
    dated reports from a single `docs/audits/README.md` index.

13. **Two renderers, two T10s (low).** `Render/Page.lean` (HTML page tree,
    T10 in `Render/Proofs.lean`) and `Render/Ui.lean` (`UiScreen`, D1–D6 and
    `T10_ui_*`) coexist. The clinician sees `UiScreen`; the legacy page is
    still exported for the replay inspector. State this in both module
    headers, or retire the legacy path.

14. **Build ergonomics (low).** The `core`/`full` rule profile is chosen by
    editing `Specs/Profile.lean`, which changes source hashes; a Lake option
    would avoid that. The WASM freshness hash could cover only the modules
    reachable from the WASM roots, or compiled output, so documentation
    edits elsewhere do not invalidate certificates.

15. **Dense code style in research and agent code (low).** `explore/` and
    parts of `agent/src` (`prompts.ts`, `run.ts`, `manual.ts`) and `scripts/`
    use single-line functions over 240 characters. Running a formatter on
    these directories would help reviewers; `app/` already reads well.

16. **Small coverage gaps in the challenge files (low).**
    `satisfies_of_checked_scalar` (the first completion fragment, cited in
    VERIFICATION.md §1) is not in any Comparator config. The deployment
    theorems (T4), FHIR theorems (T5, T11), renderer D-theorems and
    commit-reducer theorems are checked only by `lake build` and the axiom
    audit, not by Comparator. That is acceptable but should be stated where
    the README says "Proved".

### Notes on the interpreter (no action required now)

- `setCaptured` decides whether a value was superseded by comparing element
  IDs across **all** slots, then discards linked dependents on every slot.
  Today all `linkedFrom?` sources (`visitDiagnosis`, `weight`) are whole-episode
  elements, so this is harmless; a per-order-line link source would discard
  other lines' linked copies.
- `linkedSource?` falls back to the source element on **any** slot when the
  same slot has none. This is documented and conservative (prefills are
  unconfirmed), but worth keeping in mind if per-line links are added.
